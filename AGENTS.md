# so-101

`so101` is a thin CLI over LeRobot for one SO-101 leader and follower pair with two cameras, on macOS. `README.md` is the user guide. Read it before changing a command's behavior, and update it in the same change.

`docs/` holds plans for unbuilt work and notes too long for the README, each opening with a `Status:` line. Before building a feature, check `docs/` for its plan. Once it's built, move the user-facing part into the README and update `Status:`.

## Commands

- Python is pinned to 3.13: LeRobot's argument parser (draccus) breaks on 3.14.
- `uv run python -m unittest discover -s tests` runs the tests without hardware, and CI runs them on every pull request.
  - `tests/fakes.py` runs LeRobot's real follower and motor code over `FakeMotors` (rustypot 1.13 has no in-memory bus), with fake cameras and a scripted policy. Its `NoRecorder` stands in for the recorder in the controller tests that read no run from disk.
  - Control center tests submit a command, advance a tick and read the status. Assert on motor goals, the status and command results, never on private fields.
  - A LeRobot upgrade must pass them, because the controller uses LeRobot internals.
  - `tests/fakes.py` turns down SVT-AV1's and FFmpeg's logging, datasets' progress bars and two LeRobot warnings: the `max_relative_target` clamp, which some tests trigger on every tick, and the PyAV fallback on every video decode without a system FFmpeg. Undo those lines there to see that output while debugging.
- There is no linter or formatter. Without hardware, verify a change with the tests, `uv run python -m compileall -q src tests`, `--help` on each changed command, and `uv run python -c "from so_101 import settings; print(settings.load())"` for config changes.

## Hardware and billing

The arms may be plugged in. Unless the user asks, run only read-only commands: `info`, `tasks`, `check`, `scan`, `motors`, `pose` and `--help`. `check` only writes the cameras' UVC controls, which last until a camera loses power.

- These move the arm: `teleop`, `record`, `run`, `serve`, `check --live`, `record --dry-run --replay`.
- `setup-motors` and `calibrate` write to the motors.
- `pose --save-rest` and `find-port` rewrite `so101.toml`.
- `cameras` sets the cameras' UVC controls.
- `record` deletes its new session folder when nothing was saved in it (`data.remove_session`).
- `train` (unless `--target local`) and `server start` bill the user's Hugging Face credit. A server bills until `server stop`.
- `train` and `backup` upload to the Hub.

## Architecture

- **Config.** `settings.load()` reads `so101.toml` into frozen dataclasses, and `SO101_CONFIG` and `SO101_DATA_DIR` choose the file and the data folder. Ports and ids live only there. `tasks.py` reads `tasks.toml`. A new setting needs a dataclass field, a default in `load()`, and a comment in `so101.toml` if the file sets it. A `[control]` setting also needs a row in `settings.CONTROL_SETTINGS`, the one table of its default, minimum and choices, read by `settings._control` and `check.check_control`.
- **LeRobot runs as a child process.** `cli.py` parses the arguments and dispatches; the longer commands (`serve`, `runs`) and what `run` and `serve` share are in `commands/`. They build `lerobot-*` commands and run them with `console.run_lerobot`, which prints the command and filters harmless stderr. Unknown arguments pass through to LeRobot on the parsers marked `forwards=True`, which is why each `cmd_*` takes `extra`; every other command refuses them.
- **Control center** (`control/`, which `so101 serve` runs as `so101-control`). `states.py` is a pure state machine. `controller.py` is the one loop that touches the hardware and the policy, and carries out the state machine's transitions; other threads only `submit` commands to it. Its helpers sit beside it and are used only through it: `follower.py` (reads, power marks, the hold in Fault), `leader.py` (Handover, the rewind's mirror), `rewind.py`, `attempt.py` (the open attempt, one object from open to close), `commands.py` (the one table of commands and the options each takes, and taking a command in: options, page control, dispatch), `tools.py` (Run checks, Check pose), `status.py` (the status the page reads) and `wording.py` (what the operator is told as the state changes), the last two functions of the controller's state. A tick publishes the status once, at its end, then answers the commands it took, so a page's reply sees its command's effect. Scripted moves advance one tick at a time (`rollout.Move`), so Pause can cut them short. Every attempt ends through `Controller.end_attempt`. `control/main.py` loads `so101.toml` and `tasks.toml` itself; `serve` passes only per-run values, as JSON in `SO101_RUN`: the run folder, which names the task, and the `run.json` the control center writes once it's ready, with the fps, operator and policy (model, and the cloud GPU job with `--remote`); `main.require_serve_env` exits unless it's set. A new setting the control center needs goes in `so101.toml`, not in another variable. After the follower goes silent or a motor restarts, it gets no goal until it answers, then holds where it's found: any goal write turns a powered-off servo's torque back on (`docs/hardware-notes.md`).
- **`so101 run`** uses `rollout.py` instead of `lerobot-rollout`, to drive to the demos' start pose (`SO101_START_POSE`) before each attempt.
- **Preflight.** `teleop`, `record`, `run` and `serve` call `check.preflight()`, which exits on any FAIL. There is deliberately no override. Checks report through `report.Report`. In `serve`'s preflight a rest pose without `rest_pose_calibration` is a FAIL (a WARN in `check`), and a plugged-in leader's failures are WARNs (`run_checks(teleop_only=...)`), because only Teleop needs the leader.
- **Cameras** are found by `usb_id`, because OpenCV indices change on replug. Exposure and anti-flicker go through the external `uvc-util`, because macOS gives OpenCV no access to them.
- **Data is append-only.** Recorded sessions and `serve` runs are never modified. `review` writes only `edits.toml`, and `review --runs` writes only a run's `labels.toml`. The layout is in the `data.py` docstring, including the recorder's `meta-copy/<n>/meta/`, the one folder of a run it replaces while recording. The recorder finalizes a run's dataset after every saved attempt: LeRobot writes a data file's footer only at `finalize`, so a hard kill would otherwise lose the whole run. What `build` takes from runs is defined in the `control/analysis.py` docstring; raise `RULES_VERSION` when that changes (it is 5: waiting frames, where the policy sent no action, are in no cut and count toward no blame window). `analysis.read_run` reads a run's files once into a `RunRecord`, and `analysis.analyse_record` derives the analysis from it, the labels and `blame_s` without reading a file, so `review --runs` keeps the record across its decisions and the rules can be tested on small inputs.
- **SVT-AV1's macOS crash.** SVT-AV1 3.0.0, which PyAV 15.1.0 bundles, can SIGTRAP when a video encoder closes ([issue #2961](https://github.com/AOMediaCodec/SVT-AV1/issues/2961), fixed in 4.3.0). `svtsem.c` applies the upstream fix at runtime, and `svtshim.py` builds it with `cc` and restarts the process with it in `DYLD_INSERT_LIBRARIES`. A new entry point that encodes video calls `svtshim.ensure()` first, before any thread starts or stderr is filtered, and then `svtshim.require()`. A new command that records goes in `cli.VIDEO_COMMANDS` and passes `video=True` to its checks. This venv's Python children inherit the variable; start every other program with `env=svtshim.other_env()` (a test checks each subprocess call), because macOS's own arm64e programs refuse the arm64 library when System Integrity Protection is off, as on CI. Start Python children without `/bin/sh`, which drops the variable when SIP is on. The background, the measurements and how to remove it are in `docs/svt-av1-crash.md`.
- **Remote inference.** `remote.py` runs LeRobot's policy server on a labelled Hugging Face Jobs GPU, reached over SSH. `run --remote` refuses a server whose labels don't match. Policy options go in the server config, because its client rejects `--policy.*`. `remote.SERVER_IMAGE` is pinned by digest, because LeRobot publishes no image tagged for a release; no job has run it against the 0.7.0 client yet.
- **Invariants and where each is enforced.** Fix a breach at its boundary, not at the call site that showed it.
  - Never drop the arm: `Controller.tick` turns any error into a fault that holds the arm, and the loop never exits on one. Run a new tick step through `_guard`. `recorder.event` never raises: a failed write warns once per event type, a warning stderr can't take is dropped, and a field JSON can't hold is written as its `str`. `console.run_lerobot` passes SIGTERM and SIGHUP to the child as SIGINT. `follower.Arm` writes goals without LeRobot's every-camera-connected check, so a camera fault never blocks the hold or the way to rest. `main.control` registers each cleanup in an `ExitStack` as its resource is made, so every one runs, in reverse order of setup; `exit_on_signals` before the controller runs and `interrupt_on_signals` during cleanup keep a signal from skipping them. `Follower.hold_in_fault` is the one hold in Fault: only a lost follower gets none, and only `TorqueLimitChanged` leaves it, after the hold.
  - Never exit away from rest without someone at the arm: the state machine alone decides, from facts the controller gives it (a confirmation pending for `CONFIRM_S`, 30 s, and the command's source). Quit there only asks; only `exit_here` (`y` at the terminal, `states._exit_here`) exits, and only from source `terminal`. `main.quit_on_signals` submits Quit with source `signal`, so no signal or repeated Esc confirms. `Controller.submit` requires `source`, so no caller can leave it out.
  - Reset always has a way to rest: `states._reset` drives to rest from Fault and from Resting away from rest with no attempt open, once the follower answers and no motor alarm stands (`Follower.alarm`, a device problem that refuses Reset).
  - Labels land on the attempt meant: the page's sheet and the terminal's prompt (`terminal.KeyReader.asking`) send `for_attempt`, which `commands.stale_sheet` refuses for any attempt but the current one; `states._reset` refuses a Reset whose outcome has nothing to label (`Facts.outcome`, `Facts.fault_saved`) rather than drop it.
  - Never resend an old goal: `Follower.observe` checks the restart marks every tick before any goal, and `Follower.fault` and `hold_in_fault` send none of the old goals while the follower is lost: `hold_in_fault` first reads it, then marks it, and aims each motor at where it's found. In `Follower.check_marks` only a `torque_limit` back at `max_torque` is a restart; any other value is `TorqueLimitChanged`, which holds the last goal and leaves the value as found.
  - A hard kill loses only the open attempt: saved means finalized (`Recorder.save_attempt` finishes the data file before it writes `attempt_end` or counts the attempt), `data.Run.save_meta_copy` keeps the dataset's shared metadata after each finished save and `Run.meta` and `Run.info` fall back to it, `analysis.read_data` reads each Parquet file on its own, skipping one it can't read, and `build.plan_runs` skips a cut whose episode isn't in the index. `build.build` removes `build.json` before it swaps `train/`, and writes the new one to a temporary file it renames, so a kill leaves no build that claims to be current.
  - Training data says what happened: `Controller` sets an attempt's `policy_drove` only on a tick whose policy action reached the arm, and `analysis` puts waiting frames in no cut.
  - Never public: `server.Handler._send` closes the connection after every error response, and `Handler._refuse_framing` refuses any `Transfer-Encoding` and a GET that has a body, so an unread body is never parsed as another request. `Handler.timeout` closes a connection silent for 10 s. `bind` takes only `tailscale` or `127.0.0.1` (`settings.CONTROL_SETTINGS`, checked by `check.check_control`), so the page never listens on 0.0.0.0. `server.resolve_bind` decides where the page listens: the Tailscale address only from the Tailscale CLI, and never 127.0.0.1 while a route forwards raw TCP to the port. `ControlServer._watch_routes` checks the routes (`route_warning`) every 5 s off the loop, keeping the last answer when a check can't read Tailscale's status. `ControlServer.start` checks once before serving (`_first_route_check`), and on 127.0.0.1 a first check that can't read the status, with a CLI installed, refuses every request until one reads it (`ROUTES_UNREAD`), so with the Tailscale app quit the local page refuses until Tailscale runs. While a route is unsafe `Handler._refuse_caller` refuses every request, logins included. Over HTTPS, `_refuse_caller` refuses a request through Tailscale Serve without a `Tailscale-User-Login`, `resolve_bind` keeps the page off HTTPS while Funnel offers any route to the port, and the route watch refuses every request once Funnel offers one while it runs.
  - A video encoder's close never kills a process: every process that encodes video runs with `svtsem.c` loaded (`svtshim.ensure()` at each entry point, `tests/fakes.py` for the tests), and `check.check_video`, `svtshim.require()` and the preflights of `record`, `run` and `serve` refuse to run without it while `svtshim.needed()`.
  - Remote reconnects: `remote._Supervisor` restarts ssh 5 s after each exit or failed start, and a failed print can't end its thread.

## Local files

- `data/` and `outputs/` are git-ignored, and `data/` holds hours of the user's recordings. Never delete anything under either.
- `.scratch/` is git-ignored working space.
- `src/so_101/sim/` is git-ignored work from the `sim-twin` branch (PR #13). Keep it out of commits on other branches.

## Writing

The README, `docs/`, `so101.toml` comments, help text and printed messages use plain, specific sentences, with measured numbers, units and the reason behind each setting. Keep comments true when a setting changes.

Commit and PR titles are imperative, without a prefix. PRs are squash-merged with the PR number appended. PR bodies have `## Summary` and `## Testing` sections, with a table of cases and results in Testing, and say when a change hasn't run on the real arm or a remote server.
