# so-101

`so101` is a thin CLI over LeRobot for one SO-101 leader and follower pair with two cameras, on macOS. `README.md` is the user guide: read it before changing a command's behavior, and update it in the same change.

`docs/` holds long-term notes too long for the README (how built features work, hardware reference, research worth keeping), each opening with a `Status:` line. Plans, review findings and other working notes go in `.scratch/` (git-ignored), never in `docs/` or a commit. Before building a feature, check `.scratch/` for its plan. Once it's built, move the user-facing part into the README and anything worth keeping into `docs/`.

`results/` holds reviews of policy runs on the arm, kept in git: what ran, which attempts succeeded and why the others failed.
- One Markdown file per review, named `<policy>-<task>-<label>.md` (`act-block-container-baseline.md`), the label saying what the run tested. Its images go in a folder of the same name beside it, as JPEGs (quality 80 keeps a 7-attempt contact sheet near 300 KB).
- No dates or times of day, in the title, text or image names. Name a run by its command and what it tested, or by its order (`the first run`). Times within an attempt (`at 8.5 s`) stay. Never mention a local path (`outputs/`, `data/`, `.scratch/`, a scratchpad, an absolute path); copy what the review needs into its image folder.
- Judge each outcome from the camera frames, and say how. Give the setup the result depends on: the policy and revision, the block spots, the lighting.

## Commands

- `uv run python -m unittest discover -s tests` runs the tests without hardware; CI runs them on every pull request.
  - Before pushing, run them as CI does: `HF_HUB_OFFLINE=1 uv run --isolated --locked python -m unittest discover -s tests`. CI has neither the sim extra nor the `failbench` group, and the isolated env has neither, so a test that imports either without skipping fails there as it would on CI. A test that needs the sim extra subclasses `test_sim.SimTestCase`.
  - `tests/fakes.py` runs LeRobot's real follower and motor code over `FakeMotors` (rustypot has no in-memory bus), with fake cameras, a scripted policy and `NoRecorder` for controller tests that read no run from disk. Its comments say which logging it silences and how to see it. It makes the encoder's frame queue unbounded, because the tests tick faster than real time.
  - Control center tests submit a command, advance a tick and read the status. Assert on motor goals, the status and command results, never on private fields.
  - A LeRobot upgrade must pass them, because the controller uses LeRobot internals.
- There is no linter or formatter. Without hardware, verify a change with the tests, `uv run python -m compileall -q src tests`, `--help` on each changed command, and `uv run python -c "from so_101 import settings; print(settings.load())"` for config changes.

## Hardware and billing

The arms may be plugged in. Unless the user asks, run only read-only commands: `info`, `tasks`, `check`, `scan`, `motors`, `pose`, `runs`, `skills`, `server status` and `--help`. `check` writes only the cameras' UVC controls (until a camera loses power), snapshots under `outputs/check/` and the `svtshim` build in `~/Library/Caches/so101/`. `runs` writes only under `outputs/runs/`, `skills` only under `outputs/skills/`.

- Move the arm: `teleop`, `record`, `run`, `serve`, `check --live`, `record --dry-run --replay`, `sim nudge` (which also records pushes under `data/<task>/nudges/`).
- Write the motors: `setup-motors`, `calibrate`.
- Rewrite `so101.toml`: `pose --save-rest`, `find-port`. `cameras` sets the UVC controls.
- `record` deletes its new session folder when nothing was saved in it.
- `build`, and `train` when the build is stale, replace `data/<task>/datasets/whole/` (with `--skills`, `datasets/skills/`).
- `review` writes `edits.toml`, `review --runs` a run's `labels.toml`. Both serve a page on `[control] review_port` at this Mac's Tailscale address (with `bind = "tailscale"`), so any tailnet device can decide while it runs.
- Bill Hugging Face credit: `train` (unless `--target local`) and `server start`, which bills until `server stop`. Upload to the Hub: `train` (unless `--target local`), `backup`, `sim physics` (which also rewrites `sims/<task>/scene.json`).
- `sim build` rewrites `sims/<task>/` and asks the Hub for the demos' revision. `sim replay`, `score`, `check` and `eval` write only under `outputs/sim/`. `sim aim` reads the top camera, setting its controls as `check` does, and writes only under `outputs/sim/aim/` when asked.
- `serve` and `run` with the supervisor in `shadow` or `act` bill the vision keys, up to the program's `max_cost_usd` per run, and send frames to those providers. In `act` the supervisor also plays back motion, holds the arm and pauses the control center.
- `so101-failbench check` and `run` bill the keys in `.scratch/bench.env` and send recorded frames to those providers; `run` stops at `--max-cost`.

## Architecture

- **Config.** `settings.load()` reads `so101.toml` into frozen dataclasses; `SO101_CONFIG` and `SO101_DATA_DIR` choose the file and the data folder. Ports and ids live only there. `tasks.py` reads `tasks.toml`. A new setting needs a dataclass field, a default in `load()`, and a comment in `so101.toml` if the file sets it. A `[control]` setting takes its default, minimum and choices from its row in `settings.CONTROL_SETTINGS`, read by `settings._control` and `check.check_control`.
- **LeRobot runs as a child process.** `cli.py` parses and dispatches; the longer commands and what `run` and `serve` share are in `commands/`. They build `lerobot-*` commands or this repo's `so101-control`, `so101-teleoperate`, `so101-record`, `so101-replay` and `so101-calibrate`, and run them with `console.run_lerobot`, which prints the command. `console.filter_stderr` (set up in `cli.main`) drops harmless stderr for the process and its children. Parsers marked `forwards=True` pass unknown arguments to LeRobot, so each `cmd_*` takes `extra`; other commands refuse them. `run` and `serve` forward only `commands/serve.lerobot_extra`'s allow-list (`--inference.*`, `--policy.*`, `--robot.*`, `--rename_map`), because the control center sets the rest.
- **Control center** (`control/`, run by `serve` and `run` as `so101-control`). `states.py` is a pure state machine; `controller.py` is the one loop that touches the hardware and the policy and carries out its transitions (its docstring lists what other threads may call). The other modules are `main.py` (process, signals, cleanup), `server.py` and `page.html` (the control page, on `web/server.py`), `terminal.py`, `link.py`, `autopilot.py`, `previews.py`, `shedding.py`, `watch.py`, `recorder.py` and `analysis.py`. A tick publishes the status once, at its end, then answers the commands it took, so a page's reply sees its command's effect. Scripted moves advance one tick at a time (`rollout.Move`), so Pause can cut them short. Every attempt ends through `Controller.end_attempt`, except in `_force_fault`, which drops it unsaved when handling a fault fails. `control/main.py` loads `so101.toml` and `tasks.toml` itself; `serve` and `run` pass only per-run values, as JSON in `SO101_RUN` (`main.RUN_ENV`), so a new control setting goes in `so101.toml`.
- **Web pages** (`web/`, docs/reviewer.md). `web/server.py` is the one page server: `PageServer` and `Handler` hold the bind rule, the never-public checks and the route watch; each page subclasses them, adds routes in `get` and `post`, and names itself through a `Site`. A route that raises before replying gets a 500 naming it (`Handler._route`). Tests stub `ROUTES_EVERY_S`, `_tailscale` and `_tailscale_cli` on `web/server.py`, which the route checks read at each call. The reviewer (`web/review.py`, `review.html`) serves `so101 review` (`Demos`) and `review --runs` (`Runs`) in-process; `--terminal` keeps the text prompts. Every decision, from the page or a prompt, is written through `review.save` or `review_runs.apply`, so a new decision goes there, not in a handler; `tests/test_reviewer.py` makes each both ways and compares the files. `review_runs.reviewed` decides what's left to review. The page decodes video only through `dataset_io.episode_frames` and encodes none, so it needs no `svtshim`.
- **Connecting the follower.** LeRobot's `configure` cycles torque, and each servo then drives to its last goal, outside the step cap. `connect.install()` first aims every goal at where the motor is, or at its position limit for a joint up to `connect.OVERSHOOT_MAX_STEPS` past it; further past, it refuses before writing any goal. Every command that connects the follower installs it: `so101-control` and `check --live` in their process, and `teleop`, `record`, the dry run's replay and `calibrate` through the `so101-*` wrappers. A new command that connects the follower goes through one of them.
- **`so101 run`** is `so101-control` with an autopilot (`control/autopilot.py`, docs/run.md), stepped once a tick after people's commands and the link check, with that tick's `autopilot.Facts`. Its command (source `autopilot`) runs at once through `Controller.pilot_command`; `Controller.submit` refuses that source.
  - A person starts attempt 1 and the first attempt after any fault (`Facts.after_fault`); the autopilot starts the rest from rest and quits from rest after `--episodes`.
  - It never starts motion (Resume, or Reset from a pause) unless a page in control watches: `states.step` refuses both on `Facts.unwatched`, whatever `on_link_loss` says. When a page watches again it waits `reset_s`, at least `link_timeout_s` + `autopilot.RELINK_MARGIN_S`. A return to rest already started finishes even if the page is lost, so the arm is never left held in mid-air. `run` refuses `on_link_loss = "continue"`.
  - The controller ends an attempt at its time limit; the autopilot ends one only on a `done` ask and leaves every other pause to a person, so nothing moves the arm on a timer.
  - An attempt is handed to a person for good once it is unwatched while open, or on a Pause, Resume, Rewind, Teleop, Reset or Quit (Quit only when accepted) from the terminal, a signal or the page in control (`autopilot.HANDS_OVER`, from `Controller.people`), or on `answering`, which the right arrow's question and the page's Reset sheet send once. `answering` never restores a lost link (`commands._answering`). Commands from a page not in control don't count (`commands.intake`), nor does the command that starts the attempt.
  - `commands/serve.py` launches both commands; `run.json` records `mode` and, for run, `autopilot`.
- **Preflight.** `teleop`, `record`, `run` and `serve` call `check.preflight()`, which exits on any FAIL, with no override. Checks report through `report.Report`. For `serve` and `run` these are FAILs: a rest pose without `rest_pose_calibration` (a WARN in `check`), grasp thresholds that won't load, and with the supervisor on, a program that won't load or `shadow`/`act` on a task other than `vision.prompt.TASK_NAME` (`check.check_supervisor`). A plugged-in leader's failures are WARNs (`run_checks(teleop_only=...)`), because only Teleop needs it.
- **Cameras** are found by `usb_id`, because OpenCV indices change on replug. Exposure and anti-flicker go through `uvc-util`, because macOS gives OpenCV no access to them.
- **Data is append-only.** Recorded sessions and runs are never modified. The layout is in the `data.py` docstring, including the recorder's `meta-copy/<n>/meta/`. What `build` takes from runs is defined in the `control/analysis.py` docstring; raise `analysis.RULES_VERSION` when that changes.
- **SVT-AV1's macOS crash** (docs/svt-av1-crash.md). The SVT-AV1 that PyAV bundles can SIGTRAP when an encoder closes. `svtsem.c` applies the upstream fix at runtime, and `svtshim.py` builds it with `cc` and restarts the process with it in `DYLD_INSERT_LIBRARIES`. A new entry point that encodes video calls `svtshim.ensure()` before any thread starts or stderr is filtered, then `svtshim.require()`. A new recording command goes in `cli.VIDEO_COMMANDS` and passes `video=True` to its checks. Start every non-venv program with `env=svtshim.other_env()` (`tests/test_svtshim.py` checks each subprocess call), because macOS's arm64e programs refuse the arm64 library when SIP is off, as on CI. Start Python children without `/bin/sh`, which drops the variable when SIP is on.
- **Remote inference.** `remote.py` runs LeRobot's policy server on a labelled Hugging Face Jobs GPU over SSH. `--remote` refuses a server whose labels don't match (`remote.require_server`) and reads the model's files at the commit the server loaded (`remote.served_commit`, which `server start` resolves from `--revision` with `remote.hub_commit`); a local run reads them at the commit `--revision` names when it starts (`Task.policy_commit`), so a run never checks one model and drives another. Policy options go in the server config, because its client rejects `--policy.*`. pi0.5's job runs `remote.PI05_SERVER`, a script that patches LeRobot's model before starting its server, which `tests/test_remote.py` runs against stand-ins. `remote.SERVER_IMAGE` is pinned by digest; read its comment before changing it.
- **Simulated twin** (`sim/`, docs/sim.md; `uv sync --extra sim`), built for `block-container`: a top and a wrist camera, a red block, a jar and a mat. `sim build` fits `sims/<task>/` from the built demos alone, and no policy enters a fit, so a score means the same for every model.
  - `arm.py` maps the follower's numbers to MuJoCo Menagerie's SO-101 (`Units`) and does batched kinematics; `base_underside` (2.4 mm below the origin) is added to `[sim]` `mat_height`. `camera.py` is the lens both cameras use.
  - `fit.py` holds each fit; its docstrings say what pins what. `fit_top_camera` fits the top camera, its lens and the joint offsets together, starting from the last build's camera; `[sim]` `joint_offsets_deg` holds the offsets the demos can't split between joints. `fit_wrist_camera` fits the wrist camera to the fixed jaw and each demo's block seen far and near, never to the top camera's places. Colour tests are in `looks.py`, by hue and saturation.
  - `env.py` is `BlockContainerEnv`, an EnvHub `make_env`. Geoms are in rendering groups `GROUP_*`, which decide what each camera and fit draws. Each camera hands over pictures as old, and as often, as the real one (`_picture`).
  - `photo.py` replaces rendered pixels with real ones when `SO101_SIM_DEMOS` points at the built demos (every action but `build` sets it). `build` never uses them, because the colours it matches are the ones drawn without. `score` and `check` draw from the demos the fits used and compare with the others.
  - `build.BLOCK_PLACES` lists each demo's block places; `block` is the one the build chose by replaying, where the sim puts it.
  - `build.py` orders the fits and keeps those already in `scene.json` under `fits` (`--refit-cameras`, `--refit-motors` redo them), so a rebuild from the same demos changes nothing. `aim.py` needs only OpenCV and the demos' videos, so `commands/sim.py` runs it before importing the sim.
  - `scene.json` is written only by `build.py` and `physics.fit_friction`. A new scene value needs a default in `build.DEFAULTS` if `[sim]` may set it, and an entry in `tests/test_sim.py`'s `scene_files`.
  - Most of `tests/test_sim.py` skips without the sim extra and the arm model, which CI lacks, so run it locally after changing `sim/`.
- **Policy stack** (`policy/`, docs/policy-layers.md). Everything the controller steps is a `policy.base.Policy`; a `base.Layer` wraps one and forwards what it doesn't change. `policy/stack.build` composes them in one order: `engine.EngineDriver` (the only LeRobot inference code) → `perception.Perception` (always) → `skills.SkillSequencer` (skills runs) → `supervisor.layer.Supervisor` (unless `[supervisor] mode` is `off`).
  - Perception runs the grasp detector over each tick the model drove and logs `grasp` and `rule` events. Its clock and the supervisor's playback history count each driven tick as 1/`LayerContext.fps`, never real seconds, so they match the offline replays at any loop speed.
  - The controller builds a `Tick` per driven tick and reads an `Output` (action, `driver`, `skill`, `asks`, and on a playback tick `goal_frame`, after which `Controller._undo_playback` drops its Rewind history). It hands the arm over with a `Handback` saying why and whether the arm moved, and records `control.skill` and `control.driver` on every frame.
  - Only the leaf acts on a `Conditioning`. A layer's own exception is logged, announced through `maintain`, and makes it a pass-through (`Layer.safely`, which never wraps a call down the stack); one from the arm or the model reaches the controller. In a skills run a broken perception or sequencer fails `health()`, so Resume is refused.
  - Layers send no commands; they ask for a person with `Output.asks` (`Ask(kind, text)`), which pauses through `Event.POLICY_ASKED`. `tests/test_policy.py` checks the contract on every policy.
- **Supervisor** (`supervisor/`, docs/supervisor.md), the top layer: it reads the perception's signals, asks judges on `judges.DaemonPool` (so a hung call never blocks exit), plays back a miss with `control/rewind.py` only when both judges are sure (`judges.both_wrong`), holds the arm on a stuck rule, and asks for a person.
  - Every check carries the generation it was asked in, which `pause`, `run` and each hold raise, so a verdict about an arm someone moved is dropped; `pause` and `run` also drop unsent checks, a handback with `moved` forgets a confirmed release, and a check for an older close is dropped unsent.
  - `supervisor/schedule.py`'s `Schedule` decides when after_close and after_release checks fall due; `failbench.candidates` shares it, and `SchedulesMatchTest` runs both on one attempt.
  - An ask sets `_Attempt.waiting` and the handback clears it, so after a resume the rules, the miss ladder and the done check watch again. A hold asks after `hold_deadline_s`; a `done` ask waits for `Tick.at_rest` or `home_within_s`.
  - `supervisor/program.toml` (checked by `program.load`) holds its timing, judges, responses and budget; raise its `version` with any change.
- **Grasp detector** (`grasp/`). `detector.py` finds closes, carries, regrasps, releases and stuck rules in the arm's readings. It is pure, so perception, `skills`, `build --skills` and `so101-failbench candidates` all run it; `Detector.resumed` re-arms it after a handback. Thresholds are in `grasp/grasp.toml` (`[gripper]` cuts skills, `[rules]` fires stuck rules, each with a `version`). A change to how the detector reads the same thresholds raises `skills.RUN_LABEL_VERSION`; one that moves a skills cut also raises `skills.CUT_RULES_VERSION`. `grasp/replay.py` is the one offline copy of how perception feeds it live (`live_masks`, `LiveFeed`); `tests/test_replay.py` checks the two agree, so change both together.
- **Vision judges** (`vision/`): models (`models.py`), adapters (`providers.py`, the only module that imports a provider SDK), the prompt (`prompt.py`; `describe` names each request's frames), the keys reader (`env.py`) and the spending cap (`budget.py`: a call starts only if its estimate fits). The supervisor and `so101-failbench` share them, so score any prompt or adapter change with `so101-failbench` before trusting the supervisor's thresholds.
- **Skills** (`skills.py`, docs/skills.md). `[<task>.skills]` in tasks.toml names a task's parts, each a span between events that `skills.events` finds with the grasp detector. `so101 skills` checks the cuts; `build --skills` writes each kept demo's skills as episodes of `datasets/skills/` with the skill's prompt as `task` and a one-hot `observation.environment_state`, and with `--with` splits runs where the skill changes (`build.run_skills`, `skills.label_run`). `train --skills`, `serve --skills` and `run --skills` use it; a remote server's `dataset` label keeps a skills run off a whole-demo server. A change to how events are found is in `data.build_inputs`, so the build goes stale. `skills.contract` is the one list of what a skills build records and a skills model must match (`commands.policy.require_skills_contract`, checked again by `control.main.require_run_skills`).
- **Failure-detection benchmark** (`failbench/`, `so101-failbench`). Vision models judge frames of attempts against labels a person fills in to the file `candidates` writes under `outputs/failbench/`; no labels are in the repo. `run` refuses to resume a folder asked under another prompt or model settings (`runner.asked`). Provider SDKs are in the `failbench` dependency group and imported lazily, so the tests run without them.

## Invariants

Fix a breach at its boundary, not at the call site that showed it.

- **Never drop the arm.** `Controller.tick` turns any error into a fault that holds the arm, and the loop never exits on one; run a new tick step through `_guard`. `recorder.event` never raises. `console.run_lerobot` passes SIGTERM and SIGHUP to the child as SIGINT. `follower.Arm` writes goals without LeRobot's every-camera check, so a camera fault never blocks the hold or the way to rest. `main.control` registers each cleanup in an `ExitStack` as its resource is made; `exit_on_signals` and `interrupt_on_signals` keep a signal from skipping them. `Follower.hold_in_fault` is the one hold in Fault; only a lost follower gets none, and only `TorqueLimitChanged` leaves it, after the hold.
- **Never exit away from rest without someone at the arm.** The state machine decides, from a confirmation pending for `CONFIRM_S` (30 s) and the command's source. Quit there only asks; only `exit_here` (`y` at the terminal, source `terminal`) exits. Signals submit Quit with source `signal` (`main.quit_on_signals`), and `Controller.submit` requires `source`. The one exception is a silent follower in Fault (`Facts.follower_silent`), where any Quit exits at once (`Action.EXIT_LEAVING_MOTORS`) and `main.disconnect_follower` leaves the motors as they are (`Controller.leaves_motors`). `main.refuse_suspend` and `serve`'s ignored SIGTSTP keep Ctrl+Z from freezing the loop.
- **Reset always has a way to rest.** `states._reset` drives to rest from Fault, and from Resting away from rest with no attempt open, once the follower answers and no motor alarm stands (`Follower.alarm`).
- **Labels land on the attempt meant.** The Reset sheet and the right-arrow prompt send `for_attempt`, which `commands.stale_sheet` refuses for any but the current attempt; a time-limit answer is checked by `commands.stale_prompt`. `states._reset` refuses a Reset whose outcome has nothing to label (`Facts.outcome`, `Facts.fault_saved`).
- **Never resend an old goal**, because any goal write turns a powered-off servo's torque back on (docs/hardware-notes.md). `Follower.observe` checks the restart marks every tick before any goal. While the follower is lost, `Follower.fault` and `hold_in_fault` send no old goal, and `hold_in_fault` writes nothing until its reads have agreed and its supply read normal for `RESTART_SETTLE_S` (`Follower._settled`); then it aims each motor at where it is. A supply drop while servos answer is `PowerLost` (`Follower.check_power`): goals track the measured pose while reads stay low (`Follower._track`), then the last of those holds. In `Follower.check_marks` only a `torque_limit` back at `max_torque_limit` is a restart; any other value is `TorqueLimitChanged`.
- **A hard kill loses only the open attempt.** `Recorder.save_attempt` finishes the data file before writing `attempt_end`, because LeRobot writes the footer only at `finalize`. `data.Run.save_meta_copy` keeps the shared metadata after each save, and `Run.meta` and `Run.info` fall back to it. `analysis.read_data` skips a Parquet file it can't read, and `build.plan_runs` a cut whose episode isn't indexed. `build.build` writes `build.json` inside the temporary dataset folder and renames the folder into place.
- **Training data says what happened.** `policy_drove` is set only on a tick whose policy action reached the arm, and `control.driver` records who drove each frame. `analysis` puts waiting frames (the model sent nothing, or a layer drove) in no cut, and treats any layer's playback frames as suspect.
- **Never public, for every page.** The `web/server.py` docstring lists each check: `resolve_bind`, `route_warning` with `PageServer._first_route_check` and `_watch_routes` (Tailscale routes, every 1 s off the loop and off every request), and `Handler._refuse_caller`, `_refuse_framing`, `_send` and `timeout`. `bind` takes only `tailscale` or `127.0.0.1`, so a page never listens on 0.0.0.0.
- **A video encoder's close never kills a process**: the SVT-AV1 rules above, with `svtshim.ensure()` in `tests/fakes.py`.
- **Remote reconnects.** `remote._Supervisor` restarts ssh 5 s after each exit or failed start, and a failed print can't end its thread.

## Local files

`data/` and `outputs/` are git-ignored, and `data/` holds hours of the user's recordings. Never delete sessions, runs or edits under `data/`, or anything under `outputs/`; only `build` replaces what's under `datasets/`. `.scratch/` is git-ignored working space.

## Writing

The README, `docs/`, `so101.toml` comments, help text and printed messages use plain, specific sentences, with measured numbers, units and the reason behind each setting. They describe how things are, never how they got there: no dates, no "before", "now" or "used to", no earlier builds or versions to compare with. When something changes, rewrite the text to the new state and drop numbers that no longer hold. Code comments follow the same rule.

PR bodies have `## Summary` and `## Testing` sections, with a table of cases and results in Testing, and say when a change hasn't run on the real arm or a remote server.
