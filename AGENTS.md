# so-101

`so101` is a thin CLI over LeRobot for one SO-101 leader and follower pair with two cameras, on macOS. `README.md` is the user guide. Read it before changing a command's behavior, and update it in the same change.

`docs/` holds only long-term notes too long for the README: how built features work, hardware reference, and research or ideas worth keeping, each opening with a `Status:` line. Plans, review findings and other working notes go in `.scratch/`, which is git-ignored, never in `docs/` or a commit. Before building a feature, check `.scratch/` for its plan. Once it's built, move the user-facing part into the README, and anything worth keeping long term into a note in `docs/`.

`results/` holds reviews of policy runs on the arm, kept in git: what ran, which attempts succeeded and why the others failed.
- Each review is one Markdown file named `<policy>-<task>-<label>.md`, with no date, such as `act-block-container-baseline.md`; the label says what the run tested. Its images go in a folder of the same name beside it, as JPEGs (quality 80 keeps a contact sheet of 7 attempts near 300 KB).
- Leave out dates and times of day: none in the title, the text or an image's name. Name a run by its command and what it tested, or by its order when a review covers several (`the first run`), never by when it ran or where it's stored. Times within an attempt (`at 8.5 s`) stay. Never mention a local folder or path: `outputs/`, `data/`, `.scratch/`, a scratchpad or an absolute path. They're git-ignored or machine-specific, so a reader of the repo can't open them. Copy anything the review needs into its image folder.
- Judge each outcome from the camera frames, and say how. Give the setup the result depends on: the policy and revision, the block spots, the lighting.

## Commands

- `uv run python -m unittest discover -s tests` runs the tests without hardware, and CI runs them on every pull request.
  - `tests/fakes.py` runs LeRobot's real follower and motor code over `FakeMotors` (rustypot 1.13 has no in-memory bus), with fake cameras and a scripted policy. Its `NoRecorder` stands in for the recorder in the controller tests that read no run from disk. It also turns down noisy logging and warnings; its comments say which, and how to see them while debugging. It makes the video encoder's frame queue unbounded, because the tests tick faster than real time and a full queue drops frames.
  - Control center tests submit a command, advance a tick and read the status. Assert on motor goals, the status and command results, never on private fields.
  - A LeRobot upgrade must pass them, because the controller uses LeRobot internals.
- There is no linter or formatter. Without hardware, verify a change with the tests, `uv run python -m compileall -q src tests`, `--help` on each changed command, and `uv run python -c "from so_101 import settings; print(settings.load())"` for config changes.

## Hardware and billing

The arms may be plugged in. Unless the user asks, run only read-only commands: `info`, `tasks`, `check`, `scan`, `motors`, `pose`, `runs`, `skills`, `server status` and `--help`. `check` writes only the cameras' UVC controls, which last until a camera loses power, its snapshots under `outputs/check/`, and the SVT-AV1 fix it builds into `~/Library/Caches/so101/` (`svtshim`). `runs` writes only its export under `outputs/runs/`, and `skills` only its contact sheets under `outputs/skills/`.

- These move the arm: `teleop`, `record`, `run`, `serve`, `check --live`, `record --dry-run --replay`.
- `setup-motors` and `calibrate` write to the motors.
- `pose --save-rest` and `find-port` rewrite `so101.toml`.
- `cameras` sets the cameras' UVC controls.
- `record` deletes its new session folder when nothing was saved in it (`data.remove_session`).
- `build`, and `train` when the build is stale, delete and replace `data/<task>/datasets/whole/` (with `--skills`, `datasets/skills/`), each with its `build.json` inside.
- `review` writes `edits.toml`, and `review --runs` writes a run's `labels.toml`. Both serve their page on `[control] review_port` at this Mac's Tailscale address (with `bind = "tailscale"`), so any device on the tailnet can make those decisions while it runs.
- `train` (unless `--target local`) and `server start` bill the user's Hugging Face credit. A server bills until `server stop`.
- `train` (unless `--target local`) and `backup` upload to the Hub.
- `sim nudge` moves the arm: it teleoperates and records pushes under `data/<task>/nudges/`. `sim physics` uploads those to the Hub and rewrites `sims/<task>/scene.json`. `sim build` rewrites `sims/<task>/`, and asks the Hub for the demos' revision. `sim replay`, `score`, `check` and `eval` touch no hardware and write only under `outputs/sim/`. `sim aim` reads the top camera, setting its controls as `check` does, and writes only under `outputs/sim/aim/` when asked.
- `serve` and `run` with the supervisor in `shadow` or `act` (`[supervisor] mode`, or `--supervisor`) bill the same keys for its vision checks, up to the program's `max_cost_usd` per run, and send frames to those providers; in `act` the supervisor also plays back the arm's motion, holds it, and pauses the control center.
- `so101-failbench check` and `run` bill the API keys in `.scratch/bench.env` (OpenRouter, Gemini, OpenAI, TypeSafe) and send recorded frames to those providers; `run` stops at `--max-cost`.

## Architecture

- **Config.** `settings.load()` reads `so101.toml` into frozen dataclasses, and `SO101_CONFIG` and `SO101_DATA_DIR` choose the file and the data folder. Ports and ids live only there. `tasks.py` reads `tasks.toml`. A new setting needs a dataclass field, a default in `load()`, and a comment in `so101.toml` if the file sets it. A `[control]` setting takes its default from its row in `settings.CONTROL_SETTINGS` instead, the one table of its default, minimum and choices, read by `settings._control` and `check.check_control`.
- **LeRobot runs as a child process.** `cli.py` parses the arguments and dispatches; the longer commands (`serve` and `run`, `runs`, `sim`, `skills`) and what `run` and `serve` share are in `commands/`. They build `lerobot-*` commands, or this repo's `so101-control`, `so101-teleoperate`, `so101-record`, `so101-replay` and `so101-calibrate`, and run them with `console.run_lerobot`, which prints the command. `console.filter_stderr`, set up in `cli.main`, drops harmless stderr for the process and its children. Unknown arguments pass through to LeRobot on the parsers marked `forwards=True`, which is why each `cmd_*` takes `extra`; every other command refuses them. `run` and `serve` are marked too but forward only an allow-list (`commands/serve.lerobot_extra`: `--inference.*`, `--policy.*`, `--robot.*` and `--rename_map`), and refuse the rest by name, because the control center sets everything else itself.
- **Control center** (`control/`, which `so101 serve` and `so101 run` run as `so101-control`). `states.py` is a pure state machine. `controller.py` is the one loop that touches the hardware and the policy, and carries out the state machine's transitions. Its docstring lists the helpers only it uses, and what other threads may call. Beside them: `main.py` (the process, its signals and cleanup), `server.py` and `page.html` (the control page, its routes on `web/server.py`'s server), `terminal.py` (keys), `link.py` (page control and link loss), `autopilot.py` (`run`'s), `previews.py`, `shedding.py` (the loop's rate), `watch.py` (the device watch thread), `recorder.py` and `analysis.py`. A tick publishes the status once, at its end, then answers the commands it took, so a page's reply sees its command's effect. Scripted moves advance one tick at a time (`rollout.Move`), so Pause can cut them short. Every attempt ends through `Controller.end_attempt`, except in `_force_fault`, the last resort when handling a fault fails, which drops it unsaved. The controller steps the policy stack (`policy/`, below) as one policy. `control/main.py` loads `so101.toml` and `tasks.toml` itself; `serve` and `run` pass only per-run values, as JSON in `SO101_RUN` (`main.RUN_ENV`). A new setting the control center needs goes in `so101.toml`, not in another variable.
- **Web pages and the reviewer** (`web/`, docs/reviewer.md). `web/server.py` is the one page server: `PageServer` and `Handler` hold the bind rule, the never-public checks and the route watch, and each page subclasses them and adds its routes in `get` and `post`, naming itself in the messages through a `Site`; an error a route raises before replying is a 500 naming it (`Handler._route`), never a dropped connection. `control/server.py` is the control page's. The route checks read `ROUTES_EVERY_S`, `_tailscale` and `_tailscale_cli` from `web/server.py` at each call, so `tests/test_server.py` stubs them there. `web/review.py` and `review.html` are the reviewer, which `so101 review` (`Demos`) and `review --runs` (`Runs`) serve in-process on `[control] review_port`; `--terminal` keeps the text prompts. Every decision, on the page or at a prompt, is written through `review.save` or `review_runs.apply`, so both write the same files: a new decision goes there, not in the page's handler. `review_runs.reviewed` decides what's left to review: an outcome from `labels.toml` or given live. The page decodes video only through `dataset_io.episode_frames` and encodes none, so it needs no `svtshim`. `tests/test_reviewer.py` makes each decision both ways and compares the files.
- **Connecting the follower.** LeRobot's `configure` turns the torque off and on, and each servo then drives to its last goal, outside the step cap. `connect.install()` aims every goal at where the motor is first, or at its position limit for a joint up to `connect.OVERSHOOT_MAX_STEPS` past it (the servo stores the limit anyway); further past, it refuses before writing any goal. Every command that connects the follower installs it: `serve` and `run` (both `so101-control`) and `check --live` in their process, and `teleop`, `record` (its dry run's replay too) and `calibrate` through `so101-teleoperate`, `so101-record`, `so101-replay` and `so101-calibrate`, which wrap LeRobot's scripts. A new command that connects the follower goes through one of them.
- **`so101 run`** is `so101-control` with an autopilot (`control/autopilot.py`, docs/run.md): another operator, stepped by the controller once a tick, right after people's commands and the link check, with that tick's `autopilot.Facts`, whose command, with source `autopilot`, is carried out at once (`Controller.pilot_command`; `Controller.submit` refuses that source). A person starts attempt 1, and the first attempt after any fault (`Facts.after_fault`, from `Controller.fault_since_attempt`); the autopilot starts each attempt after it at rest, and never starts motion (Resume, or Reset from a pause) unless a page in control watches (`states.step` refuses both on `Facts.unwatched`, whatever `on_link_loss` says; once a page watches again it waits `reset_s`, at least `link_timeout_s` + `autopilot.RELINK_MARGIN_S`, so a restore no poll follows is lost again first), and quits from rest after `--episodes`. A return to rest it already started finishes even if the page is lost, as every return to rest does, because stopping halfway would leave the arm held in mid-air. `run` refuses `on_link_loss = "continue"` (`commands/serve.cmd_run`). The controller ends an attempt at its time limit; the autopilot ends one only on a `done` ask, and leaves every other pause to a person, so nothing moves the arm on a timer. An attempt ever unwatched while open (no page in control, or its link lost) is handed to a person for good. A Pause, Resume, Rewind, Teleop, Reset or Quit from the terminal, a signal or the page in control, accepted or refused (a Quit only when accepted), sent while an attempt is open, hands that attempt to the person (`autopilot.HANDS_OVER`, read from `Controller.people`, each command with the attempt open when it arrived), and so does `answering`, which the right arrow's question and the page's Reset sheet send once; `answering` never brings a lost link back (`commands._answering`). Nothing from a page that isn't in control counts (`commands.intake`), and the command that starts an attempt doesn't hand it over. `commands/serve.py` launches both commands; `run.json` says `mode` and, for run, `autopilot`. `rollout.py` keeps only the scripted `Move` the controller steps.
- **Preflight.** `teleop`, `record`, `run` and `serve` call `check.preflight()`, which exits on any FAIL. There is deliberately no override. Checks report through `report.Report`. In the preflight of `serve` and `run` a rest pose without `rest_pose_calibration` is a FAIL (a WARN in `check`), so are grasp thresholds that won't load, in every mode, a supervisor program that won't load, with the supervisor on, and `shadow` or `act` on a task other than `vision.prompt.TASK_NAME`, the one the judges' prompt describes (`check.check_supervisor`, on the mode `--supervisor` sets), and a plugged-in leader's failures are WARNs (`run_checks(teleop_only=...)`), because only Teleop needs the leader.
- **Cameras** are found by `usb_id`, because OpenCV indices change on replug. Exposure and anti-flicker go through the external `uvc-util`, because macOS gives OpenCV no access to them.
- **Data is append-only.** Recorded sessions and `serve` and `run` runs are never modified. The layout is in the `data.py` docstring, including the recorder's `meta-copy/<n>/meta/`, the one folder of a run it replaces while recording. What `build` takes from runs is defined in the `control/analysis.py` docstring; raise `analysis.RULES_VERSION` when that changes.
- **SVT-AV1's macOS crash.** SVT-AV1 3.0.0, which PyAV 15.1.0 bundles, can SIGTRAP when a video encoder closes ([issue #2961](https://github.com/AOMediaCodec/SVT-AV1/issues/2961), fixed in 4.3.0). `svtsem.c` applies the upstream fix at runtime, and `svtshim.py` builds it with `cc` and restarts the process with it in `DYLD_INSERT_LIBRARIES`. A new entry point that encodes video calls `svtshim.ensure()` first, before any thread starts or stderr is filtered, and then `svtshim.require()`. A new command that records goes in `cli.VIDEO_COMMANDS` and passes `video=True` to its checks. This venv's Python children inherit the variable; start every other program with `env=svtshim.other_env()` (`tests/test_svtshim.py` checks each subprocess call), because macOS's own arm64e programs refuse the arm64 library when System Integrity Protection is off, as on CI. Start Python children without `/bin/sh`, which drops the variable when SIP is on. The background, the measurements and how to remove it are in `docs/svt-av1-crash.md`.
- **Remote inference.** `remote.py` runs LeRobot's policy server on a labelled Hugging Face Jobs GPU, reached over SSH. `run --remote` and `serve --remote` refuse a server whose labels don't match (`remote.require_server`), and read the model's files at the Hub commit the server loaded, its `commit` label (`remote.served_commit`), which `server start` resolves from `--revision` (`remote.hub_commit`); a local run reads them at the commit `--revision` names when it starts (`Task.policy_commit`), so a run never checks one model and drives another. Policy options go in the server config, because its client rejects `--policy.*`. pi0.5's job runs `remote.PI05_SERVER` instead of `lerobot-policy-server`: a script that changes LeRobot's model before starting its server, which `tests/test_remote.py` runs against stand-ins. `remote.SERVER_IMAGE` is pinned by digest; read its comment before changing it.
- **Simulated twin** (`sim/`, which `so101 sim` runs through `commands/sim.py`; needs `uv sync --extra sim`). It is built for the `block-container` setup: a top and a wrist camera, a red block, a jar and a mat. `sim build` fits everything in `sims/<task>/` from the built demos and nothing else, and no policy ever enters a fit, so a score means the same for every model.
  - `arm.py` maps the follower's numbers to MuJoCo Menagerie's SO-101 (`Units`: a fitted offset per joint, and the gripper's zero) and does the arm's kinematics for many poses at once. Its `base_underside` is where the table top is in the model's axes, 2.4 mm below the origin, which `build` adds to `[sim]` `mat_height`. `camera.py` is the lens both cameras are drawn through.
  - `fit.py` holds each fit; its docstrings say what pins what. `fit_top_camera` fits the top camera, its lens and the joint offsets together, from the arm's outline, the block's sightings and the rule that every grasp lands on the mat. Each needs the other two. It also starts from the last build's camera, and `[sim]` `joint_offsets_deg` holds the offsets, which the demos can't split between the joints, while the follower's calibration stays the same. The colour tests every fit uses are in `looks.py`, by hue and saturation, so they hold through a camera that keeps colours muted and one that saturates them. A sighting is matched to where the block lay before the closing jaws slid it towards the fixed jaw (`fit.push_while_closing`, `arm.block_before_push`), not to where they held it. `fit_wrist_camera` fits the wrist camera to the fixed jaw (`fixed_jaw_core`) and to each demo's block seen from far and near, never to the top camera's places, and keeps the start whose camera best draws near blocks from where far sightings put them.
  - `env.py` is the environment (`BlockContainerEnv`, an EnvHub `make_env`). The top camera's picture is the real empty scene with the arm and block drawn on it and a real photo of the jar moved to where the jar stands; the wrist camera's is rendered whole. Geoms are in the rendering groups `GROUP_*`, which decide what each camera and each fit draws. Each camera hands over pictures as old, and as often, as the real one (`_picture`).
  - `photo.py` replaces rendered pixels with real ones when the built demos are on the computer (`SO101_SIM_DEMOS`, which every `sim` action but `build` sets): `ArmPhotos` recolours the top camera's arm, and `WristPhotos` the wrist camera's whole view, from the nearest demo frame, carrying each spot across on the thing it's part of. A block it can't paint spot by spot gets the frame's real block scaled onto it (`BLOCK_PATCH`): a rendered block at the grasp moved the ACT policy's grasp 22 mm, a painted one 5. `env.photo_from` takes the block's and jar's top camera pixels from the chosen demo's first frame. `build` never uses them: the colours it matches are the ones drawn without. `score` and `check` draw from the demos the fits used and compare with the others.
  - `demos.py` reads the built demos, and `looks.py` says which pixels of a real frame are the block, the jar and the arm.
  - `aim.py` is `sim aim`: the top camera's shift and turn against the median of the demos' first frames, from windows on fixed things, and the mat's slide beyond it. It needs OpenCV and the demos' videos, not MuJoCo, so `commands/sim.py` runs it before importing the sim.
  - A demo's block has up to four places in its layout (`build.BLOCK_PLACES`): where the top camera saw it (`seen`, where its pixels are in the demo's first frame), where the wrist camera did, and each moved clear of the demo's real jaws (`fit.clear_of_jaws`). `block` is the one the build chose by replaying, and where the sim puts it.
  - `build.py` orders the fits and keeps the ones already in `scene.json` under `fits` (`--refit-cameras` and `--refit-motors` redo them), so a rebuild from the same demos changes nothing. `score.py` and `physics.py` are `sim score` and `sim physics`; `source.py` pins the demos' Hub revision.
  - `scene.json` is read by `env.py` and written only by `build.py` and `physics.fit_friction`. A new scene value needs a default in `build.DEFAULTS` if `[sim]` in `so101.toml` may set it, and an entry in `tests/test_sim.py`'s `scene_files`.
  - `tests/test_sim.py` covers the lens, the kinematics, the environment and the drawing from real frames, on a scene and a one-colour stand-in demo it makes itself. All but the lens tests skip without the sim extra and the downloaded arm model, which CI has neither of, so run them locally after changing `sim/`.
- **Policy stack** (`policy/`, docs/policy-layers.md). Everything the controller steps is a `policy.base.Policy`; a layer (`base.Layer`) wraps one and forwards every method it doesn't change. `policy/stack.py`'s `build` is the one place that composes them, in one order: `engine.EngineDriver` (the model, the only LeRobot inference code) → `perception.Perception` (always: the grasp detector over each tick the model drove, its signals and readings carried up in each `Output`, logged as `grasp` and `rule` events; its clock, and the supervisor's playback history, count each tick the model drove as 1/`LayerContext.fps`, never real seconds, so they agree with the offline replays and with each other at any loop speed) → `skills.SkillSequencer` (for a skills run) → `supervisor.layer.Supervisor` (when `[supervisor] mode` isn't `off`). The controller builds one `Tick` per driven tick and reads an `Output` (the action, `driver`, `skill`, `asks`, and on a playback tick `goal_frame`, the frame whose measured pose it goes back to, after which the controller drops its Rewind history: `Controller._undo_playback`); it hands the arm over with a `Handback` saying why and whether the arm moved (Teleop, Rewind, Returning or a layer's playback since, unless the layer handed the arm back itself and the model drove after), and records `control.skill` and `control.driver` on every frame. Only the leaf acts on a `Conditioning` (the prompt via `set_task`, the skill one-hot in the frame it builds, and a cleared queue while it drives). A layer's own exception is logged once, announced through `maintain`, and turns it into a pass-through (`Layer.safely`, which wraps only the layer's own logic, never a call down the stack); one from the arm or the model reaches the controller unchanged. In a skills run a broken perception or sequencer fails `health()`, so Resume is refused. Layers send the controller no commands; a person is asked for with `Output.asks`, an `Ask(kind, text)`, which pauses through `Event.POLICY_ASKED`. `tests/test_policy.py` checks the contract on every policy.
- **Supervisor** (`supervisor/`, docs/supervisor.md), the stack's top layer: it reads the perception's signals, asks its judges on a worker pool (`judges.DaemonPool`, so a hung call never blocks exit), plays back a miss with `control/rewind.py` (one that stops short holds and asks for a person; a `playback` event; `control/analysis.py` treats any layer's playback frames as suspect), holds the arm on a stuck rule, and asks for a person. A playback needs both judges sure of a miss (`judges.both_wrong`). Every check carries the generation it was asked in, which `pause`, `run` and each hold raise, so a verdict about an arm someone has since moved is dropped; `pause` and `run` also drop the checks scheduled but not yet sent, and a handback with `moved` forgets a confirmed release. Each scheduled check keeps the close it was scheduled for, so one for an older close is dropped unsent. When the after_close and after_release checks fall due is `supervisor/schedule.py`'s `Schedule`, which `failbench.candidates` shares, so the benchmark scores the moments the live supervisor checks; `tests/test_supervisor.py`'s `SchedulesMatchTest` runs both on one attempt. An ask sets `_Attempt.waiting` and the controller's handback clears it, so after a person resumes the rules not yet fired, the miss ladder and the done check watch again. A hold asks for a person after `hold_deadline_s`, and a `done` ask waits for `Tick.at_rest` or `home_within_s`. Its timing, judges, responses and budget are in `supervisor/program.toml`, checked by `program.load`, which a run with the supervisor on loads; raise its `version` with any change.
- **Grasp detector** (`grasp/`): `detector.py` finds closes, carries, regrasps, releases and stuck rules in the arm's readings. It is pure, so the perception, `skills`, `build --skills` and `so101-failbench candidates` all run it, and `Detector.resumed` re-arms it after a handback. Its thresholds are in `grasp/grasp.toml` (`thresholds.load`, `[perception] thresholds`): `[gripper]` cuts skills, `[rules]` only fires stuck rules, each with its own `version`. A change to how the detector reads the same thresholds raises `skills.RUN_LABEL_VERSION` instead, which run.json and a skills build with runs record (it can move a run's labels without moving a demo's cut); one that moves a skills cut also raises `skills.CUT_RULES_VERSION`. `grasp/replay.py` is the one offline copy of how the perception feeds it live (`live_masks`, `LiveFeed`: which frames, `resumed` after a handback, including a Pause and Resume in one tick from `analysis.Attempt.handbacks`, and the model's clock: 1/fps per tick or frame fed), which `skills.label_run` and `so101-failbench candidates` replay through and `Perception` runs live; `tests/test_replay.py` checks the two against each other, so change both together.
- **Vision judges** (`vision/`): the models (`models.py`), their adapters (`providers.py`, the only module that imports a provider SDK), the prompt every model gets (`prompt.py`, whose `describe` names the frames each request carries), the keys file reader (`env.py`) and the spending cap both hold (`budget.py`: a call starts only if its estimate fits under it). The supervisor's judges and `so101-failbench` share them, so a prompt or adapter change changes what both do: score it with `so101-failbench` before trusting the supervisor's thresholds.
- **Skills** (`skills.py`, docs/skills.md). `[<task>.skills]` in tasks.toml names a task's parts, each a span between events in the arm's readings, which `skills.events` finds with the grasp detector and thresholds. `so101 skills` (`commands/skills.py`) checks the cuts; `build --skills` writes each kept demo's skills as episodes of `datasets/skills/`, each frame with its skill's prompt as `task` and a one-hot `observation.environment_state` (pi0.5 reads the prompt, ACT the one-hot), and with `--with` splits each run cut where the skill changes (`build.run_skills`, `skills.label_run`: the attempt's readings replayed through the detector, only the frames the live detector sees and on their own clock, with `control.skill` kept only on frames a skills model drove); `train --skills` trains `<policy>_so101_<task>_skills` from `<you>/so101_<task>_skills` (with `--target local`, from the local build, whose `build.json` it first copies to `outputs/train/builds/` by sha256, `data.snapshot_build`, which the model's check reads, so a rebuild never retires the model); `serve --skills` and `run --skills` stack the `SkillSequencer`. A remote server's `dataset` label keeps a skills run off a whole-demo model's server. A change to how events are found changes what a skills build holds: it's in `data.build_inputs`, so the build goes stale. `skills.contract` is the one list of what a skills build records and a skills model must match (`commands.policy.require_skills_contract`; run.json then records the skills and `[gripper]` hash checked, and `control.main.require_run_skills` checks the files against them again when `so101-control` starts): the skills as `Skill.record` gives them, the `[gripper]` hash, `CUT_RULES_VERSION` and, for a build with runs, `RUN_LABEL_VERSION`, which covers the grasp detector too.
- **Failure-detection benchmark** (`failbench/`, the `so101-failbench` command). Vision models judge frames of `serve` and `run` attempts against the labels a person fills in to the file `so101-failbench candidates` writes, under `outputs/failbench/`; no labels are in the repo. Its models, adapters and prompt are `vision/`'s, and `candidates` picks the supervisor's check moments with `supervisor.schedule`. `run` refuses to resume a folder whose answers were asked under another prompt or model settings (`runner.asked`). Provider SDKs are in the `failbench` dependency group and imported only in `vision/providers.py`, lazily, so the tests run without them. The package docstrings list the modules.
- **Invariants and where each is enforced.** Fix a breach at its boundary, not at the call site that showed it.
  - Never drop the arm: `Controller.tick` turns any error into a fault that holds the arm, and the loop never exits on one. Run a new tick step through `_guard`. `recorder.event` never raises: a failed write warns once per event type, a warning stderr can't take is dropped, and a field JSON can't hold is written as its `str`. `console.run_lerobot` passes SIGTERM and SIGHUP to the child as SIGINT. `follower.Arm` writes goals without LeRobot's every-camera-connected check, so a camera fault never blocks the hold or the way to rest. `main.control` registers each cleanup in an `ExitStack` as its resource is made, so every one runs, in reverse order of setup; `exit_on_signals` before the controller runs and `interrupt_on_signals` during cleanup keep a signal from skipping them. `Follower.hold_in_fault` is the one hold in Fault: only a lost follower gets none, and only `TorqueLimitChanged` leaves it, after the hold.
  - Never exit away from rest without someone at the arm: the state machine alone decides, from facts the controller gives it (a confirmation pending for `CONFIRM_S`, 30 s, and the command's source). Quit there only asks; only `exit_here` (`y` at the terminal, `states._exit_here`) exits, and only from source `terminal`. `main.quit_on_signals` submits Quit with source `signal`, so no signal or repeated Esc confirms. `Controller.submit` requires `source`, so no caller can leave it out. The one exception is a silent follower in Fault (`Facts.follower_silent`, from `Follower.silent`: its last read failed, not a restart its marks found), where any Quit exits at once (`Action.EXIT_LEAVING_MOTORS`): exiting can't turn those motors off, and `main.disconnect_follower` then leaves them as they are (`Controller.leaves_motors`), even if the follower answers again by then. `main.refuse_suspend` and `serve`'s ignored SIGTSTP keep Ctrl+Z from freezing the loop with the arm holding.
  - Reset always has a way to rest: `states._reset` drives to rest from Fault and from Resting away from rest with no attempt open, once the follower answers and no motor alarm stands (`Follower.alarm`, a device problem that refuses Reset).
  - Labels land on the attempt meant: the page's Reset sheet and the terminal's right-arrow prompt (`terminal.KeyReader.asking`) send `for_attempt`, which `commands.stale_sheet` refuses for any attempt but the current one, and an answer to the time-limit prompt sends the attempt it was asked about, which `commands.stale_prompt` refuses for any attempt but the one waiting; `states._reset` refuses a Reset whose outcome has nothing to label (`Facts.outcome`, `Facts.fault_saved`) rather than drop it.
  - Never resend an old goal, because any goal write turns a powered-off servo's torque back on (`docs/hardware-notes.md`): `Follower.observe` checks the restart marks every tick before any goal, and `Follower.fault` and `hold_in_fault` send none of the old goals while the follower is lost: `hold_in_fault` writes nothing to it until its reads have agreed, and its supply read normal, for `RESTART_SETTLE_S` (`Follower._settled`), because a servo that is starting up can report a wrong position; then it marks it and aims each motor at where it's found. A supply that drops while the servos still answer (`Follower.check_power`, every tick after the marks) is `PowerLost`: while the reads stay low every goal is the measured pose (`Follower._track`), never the last goal, and once they aren't low the last of those goals holds, never re-aimed, so a loaded joint can't creep down. In `Follower.check_marks` only a `torque_limit` back at `max_torque_limit` is a restart; any other value is `TorqueLimitChanged`, which holds the last goal and leaves the value as found.
  - A hard kill loses only the open attempt: saved means finalized (`Recorder.save_attempt` finishes the data file before it writes `attempt_end` or counts the attempt, because LeRobot writes a data file's footer only at `finalize`), `data.Run.save_meta_copy` keeps the dataset's shared metadata after each finished save and `Run.meta` and `Run.info` fall back to it, `analysis.read_data` reads each Parquet file on its own, skipping one it can't read, and `build.plan_runs` skips a cut whose episode isn't in the index. `build.build` writes `build.json` inside the new dataset's temporary folder and renames the folder into place, so a kill leaves the old build with its own record, or none, never a dataset beside another build's record.
  - Training data says what happened: `Controller` sets an attempt's `policy_drove` only on a tick whose policy action reached the arm, and records who drove each frame (`control.driver`, from the stack's `Output`); `analysis` puts waiting frames (the model sent nothing, or a layer drove) in no cut, and any layer's playback frames are suspect.
  - Never public, for every page: the `web/server.py` docstring lists each check. They're enforced there, in `resolve_bind` (where a page listens), `route_warning` with `PageServer._first_route_check` and `_watch_routes` (unsafe Tailscale routes, checked every 1 s off the loop and off every request, so no command waits on them), and `Handler._refuse_caller`, `_refuse_framing`, `_send` and `timeout` (each request and connection). `bind` takes only `tailscale` or `127.0.0.1` (`settings.CONTROL_SETTINGS`, checked by `check.check_control`), so the page never listens on 0.0.0.0.
  - A video encoder's close never kills a process: the SVT-AV1 rules above, with `svtshim.ensure()` in `tests/fakes.py` for the tests.
  - Remote reconnects: `remote._Supervisor` restarts ssh 5 s after each exit or failed start, and a failed print can't end its thread.

## Local files

- `data/` and `outputs/` are git-ignored, and `data/` holds hours of the user's recordings. Never delete sessions, runs or edits under `data/`, or anything under `outputs/`; only `build` replaces what's under `datasets/`.
- `.scratch/` is git-ignored working space.

## Writing

The README, `docs/`, `so101.toml` comments, help text and printed messages use plain, specific sentences, with measured numbers, units and the reason behind each setting. Keep comments true when a setting changes.

They describe how things are now, never how they got there: no dates, no "before", "now" or "used to", and no earlier builds or versions to compare with. When something changes, rewrite the text to the new state and drop numbers that no longer hold. Code comments follow the same rule.

PR bodies have `## Summary` and `## Testing` sections, with a table of cases and results in Testing, and say when a change hasn't run on the real arm or a remote server.
